# Step 7 — Recap and Exercises

> [Back to index](README.md) · Previous: [Assembling the CLI and Loop](07-assembling-the-cli-and-loop.md)

## What you built

A rebuild of [02-chat-with-web-search](../02-chat-with-web-search/)'s `chat_with_tools.py` on LangChain's native tool-calling: the same `web_search` tool, the same "at most one tool hop, bounded retries" behavior, but with `bind_tools()`/`response.tool_calls`/`ToolMessage` doing the work that `tools_prompt_block()`/regex parsing/`resolve_tool_call` did by hand. It should now match [../02-chat-with-web-search-langchain/chat_with_tools.py](../02-chat-with-web-search-langchain/chat_with_tools.py) exactly.

## Quick reference card

| Concept | Where it lives in this app |
| --- | --- |
| Tool definition | `@tool`-decorated `web_search()` |
| Native tool-calling | `llm.bind_tools(TOOLS)` in `main()` |
| Reading a tool call | `response.tool_calls` in `run_turn()` |
| Feeding a result back | `ToolMessage(content=..., tool_call_id=...)` |
| Bounded self-correction retries | `MAX_TOOL_RETRIES` in `run_turn()` — still hand-rolled |
| Unknown-tool guard | `TOOLS_BY_NAME.get(call["name"])` returning `None` |
| Who records the visible reply | `main()`, via `messages.append(AIMessage(content=answer))` — never `run_turn()` itself |

## Tradeoffs: what the framework buys you, and what it costs

| | Hand-rolled ([02-chat-with-web-search](../02-chat-with-web-search/)) | This app |
| --- | --- | --- |
| Lines spent on parsing a tool call | `try_parse_action` + regex patterns + JSON parsing | Zero — `response.tool_calls` arrives parsed |
| Lines spent on schema/validation | `WebSearchArgs` (Pydantic) + manual `model_validate` | Zero separate schema — inferred from the function signature |
| Visibility into *why* a call failed to parse | Full — you control the regex and see every intermediate string | None needed for parsing (LangChain owns it) — but also none available if the API-level parsing itself misbehaves |
| Control over the exact prompt text describing tools | Full — `tools_prompt_block()` is plain string rendering you can edit freely | None — the tool-schema wire format is generated by LangChain/the API, not something you author directly |
| Dependency footprint | `openai` + `pydantic` (already a `ddgs` dependency) | `langchain-openai`, which pulls `langchain-core`, `langsmith`, `tiktoken`, and friends |
| What still has to be hand-rolled either way | The retry loop, the unknown-tool guard, the tool's own implementation | Identical — see [run_turn()](../02-chat-with-web-search-langchain/chat_with_tools.py) |
| Reliability on small/local models | Deliberately robust to models that can't do structured tool-calling at all | Depends entirely on whether your model tag honors `tools`/`tool_calls` — untested until you run it |

The net trade is fewer lines of parsing code for less visibility into, and control over, exactly how the model is told about tools — and a real dependency-weight cost. Neither side is a strictly better engineering choice; which one you'd ship depends on whether your target model reliably supports structured tool-calling.

## Gotchas reference

| Symptom | Cause | Fix |
| --- | --- | --- |
| Model never calls the tool, even when it clearly should | Some Gemma tags/quantizations don't reliably emit tool calls through Docker Model Runner's OpenAI-compat layer | Fall back to [02-chat-with-web-search](../02-chat-with-web-search/)'s text-protocol approach, or try a different model tag |
| `[error] ... Is Docker Model Runner running?` | Docker Model Runner not running / model not pulled | See [00-local-model-setup](../00-local-model-setup/README.md) |
| `uv sync`/`uv add` pulls in far more than the hand-rolled version | `langchain-openai` brings `langchain-core`, `langsmith`, `tiktoken`, and friends | Expected — this is the real cost of the simplification; run `uv tree` for specifics |

## Discussion questions

1. `run_turn()` never appends the final visible reply to `messages` itself — `main()` always does. Why design it that way instead of having `run_turn()` own the append?
2. Which specific hand-rolled failure modes from [02-chat-with-web-search](../02-chat-with-web-search/) actually disappeared here, and which ones just moved (or stayed exactly the same)?
3. `bind_tools()` validates argument *shape* before your code runs. What's an error a tool call could still have that no amount of schema validation would catch?
4. If your model tag turns out not to support tool-calling reliably, what would you actually check before concluding that — and how would you tell "model doesn't support it" apart from "prompt/tool description needs work"?

## Exercises

Ordered easiest to hardest:

1. **Print the raw tool call before executing it.** Add a line inside the `for call in response.tool_calls:` loop in `run_turn()` that prints `call["name"]` and `call["args"]` before invoking the tool — useful for debugging, and a good way to *see* Step 3's decision happening inside the full app rather than in isolation.
2. **Add a second tool.** Pick something simple (a `calculate` tool using Python's `eval` on a restricted expression, or a `get_time` tool). Add it to `TOOLS`, and confirm `TOOLS_BY_NAME` and the retry loop handle it with no other code changes — that's the actual test of whether the tool-dispatch code is genuinely tool-agnostic.
3. **Compare token cost.** Docker Model Runner doesn't meter tokens, but you can still compare the two apps' request payload sizes (e.g. by printing `len(str(messages))` before each call) — does the hand-rolled system prompt's `tools_prompt_block()` text end up larger or smaller than what `bind_tools()` sends as a schema?
4. **Force the unknown-tool retry path deliberately**, then remove your change: temporarily rename a key in `TOOLS_BY_NAME` after construction (as suggested in [Step 5](06-retries-and-guardrails.md#try-it)) and confirm the model gets one retry with the "Unknown tool" message before the fallback response fires.
5. **Run both apps on an identical set of 5-10 prompts** (a mix of general knowledge and current-events questions) and produce a short table: which app called the tool correctly, which didn't, and where they diverged. This is the actual experiment this variant's README asks you to run — do it and write down the result.
6. **Rebuild `run_turn()` from memory.** Close this walkthrough, write `run_turn()` in a blank file from scratch — retry loop, unknown-tool guard, and all — then diff it against [chat_with_tools.py](../02-chat-with-web-search-langchain/chat_with_tools.py) only at the end.
